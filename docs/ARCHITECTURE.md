# 系统架构说明

## 1. 分层结构

```text
┌──────────────────────────────────────────────────────────────┐
│  展示层  js/ui.js                                            │
│  场景卡片渲染、结论引导文案、规则明细筛选、输入定位跳转        │
│  仅负责"如何呈现"，不产生任何判定结论                        │
├──────────────────────────────────────────────────────────────┤
│  应用层  js/app.js                                           │
│  表单 ⇄ 上下文对象读写、判定渲染、会话与记录留存、事件绑定    │
│  负责"什么时候调用引擎、结果往哪里写"                        │
├──────────────────────────────────────────────────────────────┤
│  引擎层  js/rules-engine.js   ★ 零 DOM 依赖                  │
│  规则定义、适用性判定、输入防御、结论汇总、状态与证据打包      │
│  负责"判定是什么"，可在 Node 中独立执行与回归测试            │
└──────────────────────────────────────────────────────────────┘
```

**这样分层的理由**：判定逻辑与界面彻底解耦后，同一套规则引擎可以被单测覆盖、
被回归验证、也能被替换后端调用，而不需要改动任何界面代码。

## 2. 核心数据流

```text
        ┌───────────────┐
        │  SCENES 场景  │   9 个预置合成业务样本
        └───────┬───────┘
                │ fill() 载入表单
                ▼
        ┌───────────────┐
        │   表单 UI     │
        └───────┬───────┘
                │ read() 读取为上下文对象 c
                ▼
        ┌───────────────┐
        │ invalid(c)    │   输入防御：类型 / 范围 / 逻辑一致性
        └───────┬───────┘
                │ 合法则继续，否则返回 MANUAL + 原因
                ▼
        ┌───────────────┐
        │  rules[i].ev  │   15 条规则逐条求值，异常被捕获为 MANUAL
        └───────┬───────┘
                │ rows[]
                ▼
        ┌───────────────┐
        │  汇总 take max │   BLOCK → MANUAL → COND → NOTICE → PASS
        └───────┬───────┘
                │ {rows, code}
                ▼
        ┌───────────────┐
        │  attempt[]    │   冻结：输入快照 + 配置 + 故障 + 时间 + 结论
        └───────┬───────┘
                │ pack()
                ▼
        ┌───────────────┐
        │  证据包 JSON   │   可预览 / 复制 / 下载
        └───────────────┘
```

## 3. 三个关键设计决策

### 3.1 输入必须先作防御校验

规则引擎**不被信任的输入直接调用**。所有数值先经过 `invalid()` 的类型与范围校验，
缺失、非数值、负值、逻辑冲突都会在**执行规则之前**被拦截并返回 `MANUAL`。
这避免了"用一个错误的类比值算出通过"这类静默失败。

### 3.2 每次判定都冻结上下文

`attempt` 记录会同时冻结 **输入快照**、**规则配置版本**、**故障状态** 三部分。
因此：

- 表单后续被修改时，历史判定结论不会被回溯篡改（页面会显示"结果待更新"提示）；
- 配置回放能用同一份输入对比不同规则配置，得出可解释的差异；
- 故障恢复沿用故障时的输入与配置，保留同一业务编号，形成连续的追溯链。

### 3.3 服务不可用一律降级，而非放行

三种故障注入分别对应真实的可用性风险：

| 故障 | 降级行为 |
| --- | --- |
| 规则服务超时 | **不执行任何规则**，返回 `MANUAL`，而非当作"没命中＝通过" |
| 版本库不可用 | 材料版本规则转 `MANUAL`，等待恢复后核验 |
| 证据写入失败 | 保留本地诊断记录，但**不标记**业务证据写入成功 |

> 这是本项目与"规则脚本"的本质区别：**默认不信任、默认不放行、默认留痕**。

## 4. 为什么是"最小闭环"

| 传统做法 | 本系统 |
| --- | --- |
| 规则写在制度文件里，靠人读 | 规则可执行、可回归验证 |
| 事后质检发现问题 | 事前判定并当场阻断 |
| 结论口头传达 | 结论结构化、可导出 |
| 无法还原历史判断依据 | 每次判定冻结输入与配置 |

系统刻意保持**零依赖、零构建、可离线**——这使它能够被任何人独立复现和审查，
而不是一个需要信任我说法的黑盒。
